Hybrid retrieval over Chinese supplier sheets, measured

A small, end-to-end version of the four-layer architecture: LLM header mapping with deterministic unit normalization into JSONB, BM25 and pgvector HNSW candidate generation, Reciprocal Rank Fusion and a multilingual cross-encoder, and an evaluation harness that scores every layer against ground truth. 526 supplier sheets, 104 buyer queries (English and Chinese), 4594 header rows, and an HNSW sweep on 100,000 vectors.

01Pipeline

Extract & normalize

The LLM only decides which canonical field a header means, or says ambiguous / unmapped, under a strict JSON schema. Values and units are parsed by code: 2.6Ah, 2600毫安时 and 9.6Wh all become mAh.

Candidate generation

BM25 scored in SQL over jieba + spec-aware tokens (Postgres FTS has no Chinese parser and ts_rank is not BM25), plus multilingual-e5-small in pgvector HNSW.

Fusion & rerank

Reciprocal Rank Fusion (k=60) in the same SQL statement, then bge-reranker-v2-m3 over the top 30.

Evaluation

Gold relevance from ground truth, with hard negatives: near-miss products that differ in exactly one attribute the buyer asked for. Ablations, per-language breakdown and confidence calibration.

Three findings, all visible in the table:

  • Normalized attributes are the biggest lever. Adding the extracted attributes, rendered in canonical English units, to the indexed text takes BM25 from 0.402 to 0.940. An English query for "1.5A, AU plug" can't match a sheet that says 1.5安 / 澳规 until extraction bridges the two.
  • Equal-weight RRF hurt ranking here. Dense retrieval adds candidates the lexical side misses (recall@50 0.981 → 0.993), but it is weak on exact specs, and fusing it at equal weight pulls nDCG down to 0.725. Hybrid is not automatically better. It has to be measured per query type.
  • The cross-encoder is what makes fusion worth it. It restores the ranking (0.934) and keeps the extra recall. On raw sheets alone it lifts nDCG to 0.793, the best result without extraction.

Misorder is the share of (true match, near-miss) pairs where the near-miss ranks higher. A near-miss matches the query on every attribute but one, for example 12V 1.5A with a US plug when the buyer asked for AU. The italic last row indexes ground-truth attributes instead of extracted ones, an upper bound (0.941) that shows how much retrieval quality extraction errors cost. Latency is measured on an Apple M4 with the reranker on the GPU (MPS): hybrid retrieval ≈ 19 ms including the query embedding, and the rerank adds most of the 1012 ms.

04Extraction & calibration

The model maps headers, code does the arithmetic

  • Unambiguous headers mapped correctly100.0%
  • Unambiguous headers mapped wrongly0.0%
  • Canonical values correct after normalization99.3% of 3552
  • Normalization failures (surfaced, not guessed)0
  • Ambiguous headers such as 电流 or 电压 (n=128)80% right · 20% abstained · 0% wrong
  • Expected calibration error0.053

The ambiguous headers are there on purpose: 电流 on a battery sheet could be charge or discharge current, and 电压 on an adapter could be input or output. The schema lets the model abstain, so an ambiguous row goes to review instead of into the index as a confident guess.

Hover a dot for the numbers. Every bin sits on or above the diagonal: the model is under-confident, never over-confident. Because it made no mapping errors on this set, the curve can't show where it would start to over-claim; that needs your real sheets and a few hundred labeled rows.

The filtered-search trap

A filter such as category = 'motor' AND attrs @> '{"voltage_v": 24}' (4.9% of rows) is applied after the HNSW graph walk. With ef_search = 40 the index runs out of candidates before it finds 10 that pass, and the query silently returns fewer rows. pgvector 0.8's iterative index scans fix this:

For very selective filters the right plan is often no HNSW at all: a B-tree or GIN on the filter and an exact distance sort over the survivors. To isolate the effect, this experiment forces the HNSW plan.

06The hybrid query

Lexical and semantic candidates are fused with RRF in one statement, one round trip. The BM25 subquery scores postings with the textbook formula (k1=1.2, b=0.75).

with lexical as (
    select doc_id, row_number() over (order by score desc) as rank
    from (/* BM25 subquery below */) b
),
semantic as (
    select id as doc_id, row_number() over (order by dist) as rank
    from (select id, emb_norm <=> :query_embedding as dist from products order by dist limit 50) s
)
select coalesce(l.doc_id, s.doc_id) as doc_id,
       coalesce(1.0 / (60 + l.rank), 0) + coalesce(1.0 / (60 + s.rank), 0) as rrf,
       l.rank as lexical_rank, s.rank as semantic_rank
from lexical l
full outer join semantic s on l.doc_id = s.doc_id
order by rrf desc
limit 50
BM25 subquery
with q as (select distinct unnest(:query_terms::text[]) as term),
stats as (select count(*)::float as n, avg(len)::float as avgdl from bm25_docs where field = 'norm')
select p.doc_id,
       sum( ln(1 + (stats.n - t.df + 0.5) / (t.df + 0.5))
            * p.tf * (1.2 + 1)
            / (p.tf + 1.2 * (1 - 0.75 + 0.75 * d.len / stats.avgdl)) ) as score
from q
join bm25_terms t    on t.field = 'norm' and t.term = q.term
join bm25_postings p on p.field = 'norm' and p.term = q.term
join bm25_docs d     on d.field = 'norm' and d.doc_id = p.doc_id
cross join stats
group by p.doc_id
order by score desc
limit 50

07Limits, stated plainly

  • The catalog is synthetic. It was generated with known ground truth so every number above is checkable. The header aliases, unit variants and ambiguity patterns imitate real Chinese supplier sheets, but real data will have failure modes this generator doesn't.
  • The retrieval set is small (526 sheets). The ablation shows relative gains between layers. Absolute latency and recall at production size come from the HNSW experiment, not from this table.
  • The queries are spec-style ("24V brushless DC motor 3000 rpm"), which favors lexical matching. Paraphrased or use-case queries ("battery for an e-bike") would shift weight toward dense retrieval, which is why fusion weights should come from your query logs, not from this table.
  • BM25 is implemented in SQL for transparency and CJK control. In production we would evaluate ParadeDB pg_search or pg_textsearch against it on your data.
  • Queries are not parsed into filters yet. Pulling "EU plug, 12 V" out of the query into a JSONB filter is the obvious next step, and the near-miss column is the metric it would move.
  • First step on your data: your current failure cases and any existing evaluation set. That tells us quickly whether the biggest gain is in extraction, candidate recall, filtering, fusion or reranking.
